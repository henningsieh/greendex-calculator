# Clickdummy Use-Case Traceability

Status: discovery complete for the MVP target. The clickdummy is authoritative for the outcomes below; Greendex deliberately replaces its bearer links, manual Project phases, overloaded `Ticket`, copied Claim Participants, Partner-level distance, and hard-coded rates.

## Intentional replacements

| Clickdummy choice                                            | Why it is not carried forward                                                                              | Greendex replacement                                                                                 |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Bearer links for Partner and Participant access              | No normal account security, recovery, revocation, or role scope.                                           | Better Auth accounts plus app-owned setup/registration links as entry points only.                   |
| `Ticket` stores route, amount, file, and Participants        | One overloaded record combines separate facts.                                                             | Participant Journey, Travel Cost Entry, Cost Allocation, and Proof Document.                         |
| One distance on `project_partner_orgs`                       | Participants from one Partner Organization can begin in different places.                                  | Exactly one Participant Journey per Project Participation in the MVP.                                |
| Hard-coded rates in `rateCalculator.ts`                      | Policy values change and historical Claims must remain reproducible.                                       | `@greendex/config` source values copied into immutable Project history on first Participant Journey. |
| Manual Project phases (`preparation`, `claim`, `review`)     | One Partnership's readiness should not block unrelated work; object state already says what is actionable. | Claim state/history and derived Project readiness.                                                   |
| Claim Participant snapshot and `participated` toggle         | Duplicates Project Participation facts and can diverge from costs.                                         | Claim coverage derived from Cost Allocations.                                                        |
| Host changes individual Ticket decisions and adjusted amount | Blurs Partner's claimed data and creates unnecessary partial-approval complexity.                          | Host requests Claim-level correction; Partner corrects and resubmits.                                |

## Implementation boundary

No application or database behavior is implemented by this discovery work. The next implementation specification must begin with the Claim vertical slice: Participant Journey, immutable Project funding-rule snapshot, Claim draft data, submission validation, and Partner-side authorization. Review, approval, rejection, payment, and derived dashboard readiness build on that slice.
